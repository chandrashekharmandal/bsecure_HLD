Architecture Principles

  • Modular Django Apps: Each domain (users, guards, bookings, payments, tracking, SOS) is its own app, loosely coupled.
  • ASGI Server: Daphne supports both HTTP (REST) and WebSocket (Channels) simultaneously.
  • Service Layer: Business logic lives in services.py — never in views or models.
  • Stateless API: JWT-based auth — horizontally scalable, no session state.
  • PostGIS: Guard proximity queries use native geospatial SQL with GiST indexes.

Vendor / Agency Layer

Security agencies ("vendors") can register, verify KYC documents, recruit guards under their agency, and earn commission on their guards' bookings (10–25% tiers). Guards choose to affiliate with a vendor during onboarding (vendor_selection_screen in the Guard App). See Vendor Portal for the full flow.

Service Layer Pattern

# ✅ Views delegate to services — business logic in services.py
class BookingViewSet(viewsets.ModelViewSet):
    def create(self, request):
        serializer = self.get_serializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        booking = BookingService.create_booking(
            user=request.user,
            data=serializer.validated_data
        )
        return Response(BookingSerializer(booking).data, status=201)

Authentication & OTP
Phone OTP flow, JWT strategy, bypass pin, email auth backend
▼

Phone OTP Login Flow

1
User enters phone number
POST /api/auth/send-otp/ with phone_number + role (USER or GUARD)
2
Backend generates & sends OTP
Rate check → 6-digit OTP → SHA-256 hash → store in DB (5 min TTL) → SMS via MSG91/Twilio
3
User enters OTP
POST /api/auth/verify-otp/ with phone + otp + role
4
Backend verifies & issues JWT
Hash match → mark used → get_or_create user → access token (15 min) + refresh token (30 days)
5
Client stores & uses tokens
SecureStore (mobile) / localStorage (web). All requests: Authorization: Bearer <token>

When OTP_BYPASS=True, any phone logs in with pin 123456. No SMS sent. Auto-disabled in dev & prod.

Reviews & Ratings
Post-session rating system — one review per completed booking
▼

After a booking is completed, the user submits a 1–5 star rating with an optional written review. The guard's average_rating on GuardProfile is updated automatically via a Django signal.

Review Rules

  • One review per completed booking (OneToOneField — enforced at DB level)
  • Rating: 1–5 stars (validated with MinValueValidator / MaxValueValidator)
  • Reviews can be flagged for moderation — admins review flagged entries
  • Soft data — reviews are never deleted, only flagged/hidden

REST Endpoints

POST/api/reviews/Submit rating + review for completed booking
POST/api/reviews/{id}/flag/Flag review for admin moderation

SOS & Safety System
Multi-stage escalation, dead man's switch, incident reporting
▼

SOS Trigger Methods

  • 🔴 Button hold — User/guard holds SOS button in app
  • 📳 Shake gesture — Phone shake triggers SOS
  • ⏰ Auto check-in escalation — Guard misses check-in → auto SOS at +30 min
  • 📵 Dead man's switch — Guard offline during active session (Celery every 5 min)
  • 😰 Guard distress — Guard reports own distress → notifies user + admin

Escalation Chain

🔴
T+0: SOS Triggered
DB write (<500ms) + WebSocket → admin dashboard + Celery tasks queued
📱
T+0: SMS to emergency contacts
MSG91/Twilio SMS with GPS link to all registered emergency contacts

Cost Optimization Tips

  • Use Reserved Instances for EC2 and RDS — saves 30–40% vs on-demand
  • Single AZ RDS at MVP, switch to Multi-AZ at growth stage
  • MSG91 over Twilio for India OTPs — ~10x cheaper per SMS
  • Google Maps $200/mo credit covers all MVP usage
  • S3 Intelligent Tiering for old documents — saves ~40% storage cost
  • Prefer in-house hiring over freelance/agency for long-term dev cost savings (~3x cheaper at MVP scope)
  • Free-tier AI coding assistants (e.g. Copilot Individual) can defer the $76–80/mo team cost pre-funding
